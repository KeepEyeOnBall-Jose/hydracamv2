## Current Implemented Slice

- HydraCam can parse a local `playlist.m3u8` bundle with optional `init.mp4` and referenced `.m4s` chunks.
- HydraCam can upload that complete bundle to media-timeline using `POST /api/hydracam-bridge/compat/sessions/upload-hls`.
- Media-timeline stores all HLS files through File Registry, links the playlist as event video media, and persists HLS provenance in `event_assets.metadata_blob`.
- Media-timeline registers HLS files with recording-scoped File Registry names, avoiding collisions between separate recordings that all use local names such as `playlist.m3u8` and `init.mp4`.
- Media-timeline treats `sessionGuid + deviceId + recordingId` as the finalized HLS upload identity when `recordingId` is supplied, so retrying the same completed bundle returns the existing playlist stream instead of creating duplicate File Registry uploads.
- Media-timeline exposes event-scoped playback playlists at `/api/data-model/videos/:id/hls/playlist.m3u8?eventId=...`, and the frontend video player loads them through native HLS or `hls.js`.
- HydraCam can include optional `nativeTimingMetadataJson`; media-timeline stores it as `nativeTimingMetadata` for future NTP/timestamp sync work.
- HydraCam has a Flutter/Android fixed-camera HLS capability probe and a tested Dart start/stop recording contract. Android defaults to `recorderMode: synthetic_local`, advertises `supportedRecorderModes: ["synthetic_local", "camera2_hls"]`, and routes explicit `cameraId` requests to Camera2 HLS recording.
- HydraCam now has Android-native HLS playlist/chunk naming, fMP4 init segment, H.264 SPS/PPS-to-`avcC` conversion, Annex B media-sample conversion, encoded-sample HLS finalization, and fMP4 media fragment writers under `com.amaia23.hydracam.fixedcamera`, covered by Android unit tests.
- HydraCam has a first Camera2/MediaCodec/AudioRecord adapter that buffers encoded samples and finalizes an HLS bundle on stop. This is compiled and unit-covered at the writer/formatting boundary, but it still needs emulator/hardware runtime proof before production claims.
- HydraCam has a finalized HLS bundle retry queue. Finalized native recording results can feed that queue directly, and the local `scripts/upload_hls_bundle.dart` proof path now uses the queue with optional raw native timing metadata.
- Local proof exists at `logs/verification-runs/20260619-local-fixed-camera-hls-upload/`; duplicate finalized upload proof exists at `logs/verification-runs/20260619-live-hls-idempotency-proof/`; valid HLS browser playback proof exists at `logs/verification-runs/20260619-live-hls-playback-proof/`.

## Recommended Port Order

1. Keep the multipart HLS bundle route as the first production-compatible fixed-camera lane.
2. Prove the explicit-`cameraId` Camera2 HLS path on Android emulator/hardware, first without audio if permissions/audio routing are noisy, then with audio.
3. Upload the Camera2-generated finalized HLS bundle through the existing media-timeline bridge and verify playback.
4. Populate `nativeTimingMetadataJson` from real recorder/NTP/camera timestamps before multi-camera sync claims.
